# دروازه هوش مصنوعی سازمانی — فاز ۱

> Enterprise AI Security Gateway · Phase 1 — Chatbot UI + Gateway Proxy

یک رابط گفت‌وگوی مینیمال و حرفه‌ای (شبیه ChatGPT و z.ai) که درخواست کاربر را
از طریق بک‌اند سایت ما به یک مدل زبانی خارجی ارسال می‌کند و پاسخ را به‌صورت
**زنده (Stream)** در همان سایت نمایش می‌دهد.

```text
   کاربر  →  سایت ما (فرانت‌اند)  →  /api/chat (دروازه)  →  مدل زبانی خارجی (API)
                                          ↑                       ↓
                                   کنترل‌های امنیتی        پاسخ Stream شده
                                   (فازهای بعدی)                ↓
                            نمایش مرحله‌به‌مرحله در چت  ←────────┘
```

در فاز ۱، هدف این است که کاربران به‌جای مراجعه مستقیم به سایت ChatGPT، از
سایت سازمانی ما استفاده کنند. در فازهای بعدی، لایه‌های امنیتی (DLP،
طبقه‌بند معنایی، Policy Engine و Local LLM) طبق سند `PROJECT_CONTEXT.md`
دقیقاً در همین نقطه (`/api/chat`) قرار می‌گیرند.

## ویژگی‌ها

- 💬 **رابط چت مینیمال و حرفه‌ای** — شبیه ChatGPT/z.ai با هدر چسبان، ناحیه
  پیام‌های اسکرول‌شونده و کادر ورودی چسبان به پایین.
- ⚡ **پاسخ زنده (Streaming)** — پاسخ مدل کلمه‌به‌کلمه و به‌صورت مرحله‌به‌مرحله
  با پروتکل **Server-Sent Events (SSE)** نمایش داده می‌شود.
- 🇮🇷 **پشتیبانی کامل از فارسی و راست‌چین (RTL)** — فونت Vazirmatn، جهت RTL
  و رابط فارسی.
- 📝 **رندر Markdown** — هدینگ، لیست، متن پررنگ، کد درون‌خطی و بلوک کد با
  دکمه کپی و تشخیص زبان.
- 🌙 **حالت تاریک/روشن** — با `next-themes` و ذخیره ترجیح کاربر.
- 📱 **واکنش‌گرا (Responsive)** — موبایل و دسکتاپ.
- ⌨️ **میانبرهای کیبورد** — `Enter` برای ارسال، `Shift+Enter` برای خط جدید.
- 🛑 **توقف تولید** — امکان لغو استریم در حین پاسخ‌دهی.
- 📋 **کپی پاسخ و کپی کد** — با یک کلیک.
- 🧠 **حافظه گفت‌وگو** — تاریخچه مکالمه در همان نشست نگه‌داری و به مدل
  ارسال می‌شود (با سقف ۳۰ پیام برای کنترل مصرف توکن).
- 🛡️ **معماری دروازه‌محور** — تمام ترافیک از `/api/chat` عبور می‌کند تا در
  فازهای بعدی کنترل‌های امنیتی در آن قرار گیرند.

## معماری و نحوه کارکرد

### جریان درخواست

```text
1. کاربر پیام را در فرانت‌اند می‌نویسد و دکمه ارسال را می‌زند.
2. هوک use-chat پیام کاربر را به state اضافه می‌کند و یک پیام دستیار
   «در حال تولید» می‌سازد.
3. یک POST به /api/chat با کل تاریخچه گفت‌وگو (شامل system prompt) ارسال می‌شود.
4. بک‌اند /api/chat:
   a. پیام‌ها را اعتبارسنجی و نرمالایز می‌کند.
   b. تاریخچه را به ۳۰ پیام اخیر محدود می‌کند (مدیریت توکن).
   c. با z-ai-web-dev-sdk درخواست را با stream:true به مدل خارجی می‌فرستد.
   d. جریان SSE upstream را می‌خواند و delta ها را دوباره به‌صورت SSE
      به فرانت‌اند ارسال می‌کند.
5. فرانت‌اند delta ها را دریافت کرده و به‌صورت پیش‌رونده به محتوای پیام
   دستیار اضافه می‌کند (افکت تایپ زنده).
6. پس از اتمام استریم، پیام نهایی می‌شود و دکمه‌های کپی ظاهر می‌شوند.
```

### پروتکل استریم (SSE)

بک‌اند پاسخ را با `Content-Type: text/event-stream` برمی‌گرداند. هر رویداد
به این شکل است:

```text
data: {"type":"delta","content":"کلمه‌ای از پاسخ "}\n\n
data: {"type":"delta","content":"دیگر"}\n\n
data: {"type":"done"}\n\n
```

سه نوع رویداد وجود دارد:

| `type`   | توضیح                                       |
| -------- | ------------------------------------------- |
| `delta`  | یک تکه متن برای اضافه شدن به پاسخ دستیار     |
| `done`   | استریم با موفقیت تمام شد                    |
| `error`  | خطایی رخ داد (فیلد `message` توضیح می‌دهد)  |

### نقش دروازه

نقطه کلیدی این است که **مدل خارجی هرگز کاربر را مستقیماً نمی‌بیند**. تمام
ترافیک از `/api/chat` عبور می‌کند. این طراحی عمدی است تا در فازهای بعدی،
طبق `PROJECT_CONTEXT.md`، کنترل‌های امنیتی زیر دقیقاً قبل از فراخوانی مدل
خارجی قرار گیرند:

```text
request → Authentication → Normalization → Deterministic DLP
       → Semantic Classifier → Policy Engine → ALLOW / LOCAL / BLOCK
```

در فاز ۱، مسیر همیشه `ALLOW → External LLM` است.

## API مرجع

### `POST /api/chat`

ارسال یک درخواست چت و دریافت پاسخ به‌صورت Stream.

**درخواست:**

```json
{
  "messages": [
    { "role": "system", "content": "تو یک دستیار مفید هستی." },
    { "role": "user", "content": "سلام، حالت چطوره؟" }
  ]
}
```

| فیلد       | نوع     | توضیح                                       |
| ---------- | ------- | ------------------------------------------- |
| `messages` | آرایه   | **الزامی.** لیست پیام‌های گفت‌وگو           |
| `messages[].role` | `"system" \| "user" \| "assistant"` | نقش پیام |
| `messages[].content` | string | متن پیام (نخالی)                          |

**پاسخ:**

`Content-Type: text/event-stream; charset=utf-8`

```text
data: {"type":"delta","content":"سلام"}\n\n
data: {"type":"delta","content":"! "}\n\n
data: {"type":"done"}\n\n
```

در صورت خطا:

```text
data: {"type":"error","message":"توضیح خطا"}\n\n
```

**مثال با cURL:**

```bash
curl -N -X POST http://localhost:3000/api/chat \
  -H "Content-Type: application/json" \
  -d '{"messages":[{"role":"user","content":"سلام"}]}'
```

> فلگ `-N` بافرینگ را غیرفعال می‌کند تا خروجی استریم را زنده ببینید.

## نکات توسعه و عیب‌یابی

### سرور بالا نمی‌آید

- مطمئن شوید پورت ۳۰۰۰ اشغال نیست: `lsof -i :3000`
- اگر نمونه‌ای از قبل در حال اجراست، ابتدا آن را متوقف کنید.

### پاسخ استریم نمی‌شود (همه‌چیز یک‌جا می‌آید)

- مطمئن شوید header `Cache-Control: no-cache` ارسال می‌شود (در `route.ts` هست).
- اگر پشت پروکسی/CDN هستید، بافرینگ را غیرفعال کنید (header
  `X-Accel-Buffering: no` در پاسخ تنظیم شده است).

### خطای `Module not found: '@/components/...'`

- `bun install` را دوباره اجرا کنید.
- مطمئن شوید `tsconfig.json` دارای `paths: { "@/*": ["./src/*"] }` است.

### خطای SDK یا خالی بودن پاسخ

- `z-ai-web-dev-sdk` فقط سمت سرور قابل استفاده است؛ هرگز آن را در کامپوننت
  کلاینت `import` نکنید.
- لاگ سرور را در `dev.log` بررسی کنید.

### تغییرات اعمال نمی‌شود (Hot Reload کار نمی‌کند)

- فایل را ذخیره کرده‌اید؟ Next.js Fast Refresh معمولاً زیر ۱ ثانیه اعمال می‌شود.
- در صورت نیاز سرور را ری‌استارت کنید: `Ctrl+C` سپس `bun run dev`.

### فونت فارسی بارگذاری نمی‌شود

- نیاز به اتصال اینترنت دارید (دانلود از Google Fonts در زمان بیلد اول).
- پس از بارگذاری اول، فونت کش می‌شود.

### بررسی لاگ سرور

```bash
tail -f dev.log
```

## نقشه راه فازهای بعدی

طبق `PROJECT_CONTEXT.md`، این پروژه یک **دروازه امنیتی** است. فاز ۱ فقط
بستر چت و پروکسی را فراهم می‌کند. فازهای آینده:

- [ ] **فاز ۲ — تشخیص قطعی (Deterministic DLP):** تشخیص API Key، JWT،
  رمز عبور و الگوهای حساس با regex قبل از ارسال به مدل خارجی.
- [ ] **فاز ۳ — طبقه‌بند معنایی:** یک مدل محلی (Local LLM) برای تشخیص
  محتوای محرمانه بدون الگوی مشخص.
- [ ] **فاز ۴ — Policy Engine:** تصمیم‌گیری نهایی `ALLOW / LOCAL / BLOCK`
  بر اساس خروجی DLP و طبقه‌بند.
- [ ] **فاز ۵ — Local LLM:** اجرای مدل محلی برای پردازش درخواست‌های حساس
  داخل زیرساخت سازمان.
- [ ] **فاز ۶ — امنیت خروجی (Output Security):** فیلتر کردن پاسخ مدل برای
  جلوگیری از نشت اطلاعات.
- [ ] **فاز ۷ — احراز هویت، لاگ ممیزی و داشبورد مدیریت.**

> **قانون امنیتی غیرقابل تغییر:** داده‌های حساس هرگز نباید به مدل خارجی
> برسند. در فاز ۱ این کنترل هنوز پیاده نشده، بنابراین **از ارسال اطلاعات
> محرمانه در فاز ۱ خودداری کنید.**
